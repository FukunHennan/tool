## 需求概述

建设一套长期可扩展的工具系统，整体形态参考“统一平台 + 多个相对独立工具”的架构。当前阶段不急于一次性定义完整的平台边界、工具清单或最终技术形态，而是先持续开发有实际价值的工具，在工具数量和使用场景逐步增加后，观察它们之间的共性，再提炼统一入口、工具管理、账号、下载和部署等平台能力。

平台的组织方式可以参考微信与小程序、以及硬件工具平台的统一入口思路，但这些产品只用于理解“多工具系统”的架构形态。后期工具的类型、功能和交互由本项目自身规划决定，不要求复刻任何参考产品，也不要求后期工具与参考产品属于同一类别。

当前已有的 PCB 物料柜是一个可独立运行的工具。串口助手、在线编程、在线调试等是未来可能开发的工具方向，暂不提前确定开发顺序或首期边界。

## 当前阶段目标：持续开发工具

### P0 - 当前必须遵守的原则

- [ ] 优先开发真实、有明确用途的工具，而不是先构建完整的平台系统。
- [ ] 每个工具先保证自身功能、交互和可用性，允许工具拥有独立的页面和数据模型。
- [ ] 记录各工具在入口、配置、存储、权限、部署和下载方面的共同需求。
- [ ] 在工具数量增加或出现明显重复需求后，再回顾并提炼平台公共能力。
- [ ] 平台能力应由真实工具需求驱动，避免为了预想中的工具提前增加复杂系统。

### P1 - 逐步形成的平台能力

- [ ] 当工具数量和需求足够明确后，形成统一的网站入口和工具目录。
- [ ] 为工具补充统一的名称、简介、分类、状态和运行方式描述。
- [ ] 根据工具实际需求决定在线工具、下载工具或本地运行工具的组织方式。
- [ ] 根据多个工具的共性决定统一导航、工具详情、版本信息和发布流程。
- [ ] 根据真实用户和部署经验，再评估账号、同步、权限和数据管理。

### P2 - 未来可能出现的能力

- [ ] 工具收藏、最近使用、搜索和个性化组织。
- [ ] 工具版本管理、发布后台、下载文件管理和运行环境检测。
- [ ] 在线编程、在线调试、设备控制等硬件相关工具形态。
- [ ] 统一的工具扩展机制或类似小程序的加载方式。

## 工具开发范围

后期工具功能不预先限定。工具可以面向硬件开发、嵌入式开发、文件处理、数据处理、效率提升或其他实际需求。每个工具根据自己的目标用户和任务确定功能，平台只在出现稳定共性后提供必要的公共能力。

### 已有工具

- PCB 物料柜：当前已有的可视化物料管理工具，可作为后续平台化观察样本。

### 可能开发的工具

- 串口助手：可能用于浏览器串口连接、参数配置、数据收发和调试。
- 在线编程工具：未来根据具体设备和实际需求评估。
- 在线调试工具：未来根据具体调试器、设备和使用场景评估。

以上列表是方向记录，不是承诺的功能清单，也不代表开发顺序。

## 非功能需求

- **演进性：** 允许需求随着工具实践不断修订，不把早期假设当作最终平台设计。
- **可扩展性：** 新工具应能够独立开发和运行；平台公共能力在需求稳定后再抽取。
- **独立体验：** 工具可以使用平台公共入口，也可以根据任务复杂度拥有自己的工作区和交互流程。
- **兼容性：** 每个工具单独明确其浏览器、操作系统、硬件和运行环境要求。
- **安全与隐私：** 访问本机设备、文件或其他敏感能力必须由用户显式触发和授权；工具不应默认上传用户数据。
- **可靠性：** 工具不可用、权限不足、环境不满足或运行失败时，必须提供明确状态。
- **部署目标：** 最终希望部署到服务器，让用户通过网站访问；具体部署方式等工具需求更清晰后确定。

## 边界与约束

- **当前不锁定首期平台范围：** 不预先决定先做完整平台骨架、接入物料柜还是开发串口助手。
- **当前不锁定工具顺序：** 工具按实际价值、开发条件和用户反馈推进。
- **平台架构延后收敛：** 等出现足够多的工具和重复需求后，再确定平台的公共模块与技术架构。
- **功能不照搬：** 波特律动串口助手、嘉立创 K230 在线编程工具、嘉立创 DAP 在线调试仅用于参考多工具产品的组织方式或使用体验，不构成必须实现的功能清单。
- **首期暂不包含：** 完整账号体系、支付、社交、多人协作、小程序运行时和复杂发布后台，除非后续真实需求明确提出。
- **技术限制：** 在线工具能否访问本机设备取决于浏览器、操作系统、安全上下文和用户授权，不能假设所有工具都能纯网页实现。

## 阶段性验收标准

### 工具持续开发

- Given 一个工具有明确用途和目标用户，When 开发该工具，Then 工具能独立运行并完成自身核心任务。
- Given 工具需要特殊浏览器、硬件或操作系统能力，When 用户使用工具，Then 工具明确展示前置条件和失败状态。
- Given 一个工具完成阶段性开发，When 复盘其实现，Then 记录可复用能力和仅属于该工具的特殊逻辑。

### 平台能力提炼

- Given 已经积累了多个工具，When 对工具进行横向比较，Then 能识别真实重复的入口、配置、权限、存储、版本或部署需求。
- Given 某项能力只被单个工具使用，When 评估是否平台化，Then 可以继续保留在工具内部，不强行抽取。
- Given 多个工具出现稳定共性，When 平台提炼该能力，Then 新工具可以复用它，同时不限制工具自身的独立交互。

### 未来工具平台

- Given 平台公共能力已经由真实工具需求验证，When 用户访问系统，Then 用户可以从统一入口发现并进入多个工具。
- Given 不同工具的功能差异较大，When 用户进入某个工具，Then 工具保留适合自身任务的工作流，不被统一界面强行限制。

## 当前工作方式

1. 选择一个有明确价值的工具并完成其核心功能。
2. 在开发过程中记录工具特有需求和可能的跨工具共性。
3. 工具完成后进行一次简短复盘，不急于抽象成平台能力。
4. 当工具数量和重复需求足够多时，再单独进行平台需求分析和方案设计。

## 当前不需要决定的事项

- 平台最终名称和完整视觉体系。
- 平台第一阶段的固定工具清单。
- 工具统一采用独立页面、嵌入式工作区还是统一壳层加载。
- 是否需要账号、同步、权限、支付或发布后台。
- 串口助手、在线编程和在线调试的具体开发顺序。
- 最终服务器架构、域名和运维方案。
