# 协议扩展指南

## 1. 为什么协议层独立

串口只提供连续字节流。协议层负责确定帧边界、校验内容并转换为业务数据。将协议逻辑与 React 组件或 Web Serial API 分离，可以独立测试半包、粘包、噪声字节和校验错误。

## 2. 建议接口

```ts
export interface FrameDecoder<T> {
  push(chunk: Uint8Array): DecodeResult<T>;
  reset(): void;
}

export interface FrameEncoder<TCommand> {
  encode(command: TCommand): Uint8Array;
}

export interface DecodeResult<T> {
  frames: T[];
  errors: ProtocolError[];
}
```

`push()` 内部保留未完成帧，下次收到数据后继续解析。解码错误不应让整个接收循环崩溃。

## 3. 自定义二进制协议模板

待设备协议确定后填写：

| 字段 | 偏移 | 长度 | 字节序 | 说明 |
| --- | ---: | ---: | --- | --- |
| 帧头 | 待定 | 待定 | - | 固定同步字 |
| 命令字 | 待定 | 待定 | - | 消息类型 |
| 数据长度 | 待定 | 待定 | 待定 | Payload 长度或全帧长度 |
| Payload | 待定 | 可变 | 待定 | 业务数据 |
| 校验 | 待定 | 待定 | 待定 | CRC/校验和 |
| 帧尾 | 可选 | 待定 | - | 如协议需要 |

必须同时确认：最大帧长、超时时间、请求响应关系、序列号规则、重试次数及设备错误码。

## 4. 解析策略

通用解析循环：

1. 将新数据追加到内部缓冲区。
2. 搜索合法帧头；帧头前的噪声作为可诊断错误丢弃。
3. 数据不足以确定长度时等待下一数据块。
4. 拒绝超过最大帧长的长度值，避免异常数据导致内存持续增长。
5. 数据完整后执行校验。
6. 校验成功则输出帧并从缓冲区移除。
7. 校验失败时按协议规定重新同步，而不是简单清空所有后续数据。

## 5. Modbus RTU 扩展

如果设备使用 Modbus RTU，需要进一步确定：

- 从站地址范围。
- 使用的功能码和寄存器表。
- 寄存器字节序及多寄存器数值排列。
- 帧间隔判断策略。
- CRC-16/MODBUS 实现和测试向量。
- 请求超时、异常响应和重试策略。

寄存器地址、比例系数、单位、读写权限应该以数据表配置，不分散写在页面组件里。

## 6. 测试向量要求

每种协议至少提供：

- 一帧合法请求和响应。
- 分成多个 chunk 到达的合法帧。
- 多帧粘连。
- 错误校验值。
- 非法长度。
- 帧头前噪声。
- 最大长度帧。

测试向量需写清十六进制输入、预期领域消息和预期错误。
